Inspecting NumPy Embeddings

Embeddings are not magic — they are plain numpy.ndarray objects full of float32 numbers. This page shows you exactly what is inside, how the .npy file on your disk is laid out, and how to interrogate every byte of it. All demos run live in your browser on realistic (synthetic) 384-dim vectors.

Section 1

What exactly is an embedding array?

When your code runs model.encode(["A bear attacks a man"]), the transformer reduces the sentence to one point in a 384-dimensional space. NumPy hands you that point as an ndarray — a thin Python wrapper around a contiguous block of C memory. Five attributes tell you everything about that block:

AttributeValue in this projectWhat it means
type(emb)numpy.ndarray A strided view over a raw memory buffer — not a Python list. Indexing, slicing, and arithmetic are vectorized C loops.
emb.dtypefloat32 Each dimension is a 4-byte IEEE-754 float. 7 significant decimal digits, range ~±3.4×1038. Half the memory of float64, plenty for ML.
emb.shape(384,) 1-D vector with 384 elements. The trailing comma matters: (384,) is a 1-tuple — a vector, not a matrix. A batch is (5000, 384).
emb.strides(4,) Bytes to jump per index step: 4 bytes = one float32. For a (5000, 384) C-contiguous matrix it is (1536, 4) — 384×4 = 1536 bytes per row.
emb.nbytes1536 Total payload: 384 × 4 = 1,536 bytes = 1.5 KB per document. 5,000 movies → ~7.3 MB. Trivially small.
Verified live in this project: encoding "A bear attacks a man in the wilderness" with all-MiniLM-L6-v2 returns float32, shape (384,), values in [-0.160, 0.140], and L2 norm 0.99999994. MiniLM normalizes every output to the unit sphere — that is why dot product = cosine similarity here, with no extra normalization step.
Why float32 and not float64? GPU/CPU inference happens in float32, and embeddings only need to rank documents relative to each other. Doubling precision would double RAM, disk, and bandwidth while changing essentially zero search results.

Section 3

Anatomy of the .npy file on disk

Your build_embeddings() calls np.save("cache/movie_embeddings.npy", self.embeddings). That file is not pickled and not text — it is a tiny header followed by a raw dump of the array's memory. Byte by byte:

934E 55 4D 50 59 0100 76 00 7B 27 64 65 73 63 72 27 3A 20 27 3C 66 34 27 2C 20 27 66 6F 72 74 72 61 6E 5F 6F 72 64 65 72 27 3A 20 46 61 6C 73 65 2C 20 27 73 68 61 70 65 27 3A 20 28 35 30 30 30 2C 20 33 38 34 29 2C 20 7D … raw float32 payload …
BytesFieldMeaning
0–5magic \x93NUMPYIdentifies the format. np.load checks this first.
6–7version 01 00Format v1.0.
8–9header len 76 00Little-endian uint16: the header dict is 118 bytes.
10–127header dictA literal Python dict: {'descr': '<f4', 'fortran_order': False, 'shape': (5000, 384), } — dtype, byte order, and shape. The entire metadata of your embedding store fits in one line of ASCII.
128…payload5000 × 384 × 4 = 7,680,000 bytes of raw float32, row-major. Row i starts at byte 128 + i×1536.
Consequence: because the payload is a fixed-stride memory dump, np.load(path, mmap_mode='r') can memory-map the file — the OS pages rows in on demand. You can inspect a 10 GB embedding matrix on a laptop with 8 GB RAM. embs[42] reads only that row's 1,536 bytes from disk.
Gotcha: np.save is not portable like JSON. It assumes NumPy on the reading side and stores native dtype/layout. Perfect for a local cache (your use case), wrong for an API response or cross-language pipeline — that's what JSON/Parquet are for.

How big is the embedding store, really?

Storage is pure arithmetic: bytes = 128 (header) + N × 384 × 4. Compare against the naive alternative — serializing the same floats as JSON text (~15 characters per number). Drag the slider:

Speed, not just size: loading a .npy is a header parse + one read() (or mmap) into a preallocated buffer — no tokenizing, no float parsing. Loading the JSON version at 1M docs would take seconds and ~4× peak RAM. This is why np.save is the right call for your cache.
Section 5 · Live Lab

The Dot Product Lab — where similarity comes from

Semantic search is one line: scores = embeddings @ query_vec. Because every vector is unit-normalized, each score is the cosine of the angle between two movies. Pick a pair and watch the score, plus which dimensions contribute most to it:

·

dot product (= cosine sim)
—
—
top contributing dims
—
dims where a[i]·b[i] is largest
The mechanic: a·b = Σ a[i]×b[i] over 384 terms. A dimension only pushes the score up when both vectors agree in sign there. Two survival movies share the same "genre signature" across hundreds of dims, so thousands of tiny products accumulate into a high score. Unrelated movies have uncorrelated signs — products cancel out around zero.

Equivalent NumPy (this is the whole search ranking):

q = s.generate_embedding("wilderness survival bear attack")
scores = embeddings @ q          # (5000,) — one score per movie, in one C loop
top5 = scores.argsort()[::-1][:5]  # indices of the 5 best matches

Similarity Heatmap — the matrix E @ E.T

Compute every pairwise dot product at once with one matrix multiply and the structure of your corpus becomes visible: blocks of high similarity along the diagonal = genres. Hover any cell.

Try it on your real data: S = embs @ embs.T gives a (5000, 5000) float32 matrix — 100 MB, fine in RAM. Rows where the off-diagonal values are unexpectedly high reveal near-duplicate descriptions; a dead-flat row hints at a broken/empty document. The heatmap is a data-quality tool, not just a visual.
Section 7 · Reference

Inspection Cheat Sheet — run these yourself

Everything on this page reduces to a handful of one-liners. After you run build_embeddings() once (which creates cache/movie_embeddings.npy), open a REPL from the project root with uv run python and interrogate away:

import numpy as np

# --- Load & identity ---
embs = np.load("cache/movie_embeddings.npy")
embs.shape, embs.dtype, embs.nbytes   # (5000, 384), float32, ~7.3MB
embs.flags['C_CONTIGUOUS']           # True → rows laid out back-to-back

# --- Health checks ---
np.isnan(embs).any()                  # False — no poisoned vectors
np.isfinite(embs).all()               # True — no Inf
norms = np.linalg.norm(embs, axis=1)  # (5000,) — one norm per movie
norms.min(), norms.max()              # ≈ (1.0, 1.0) for MiniLM

# --- Slicing = free views (no copy!) ---
embs[0]            # movie 0's full 384-dim vector
embs[0, :5]       # its first 5 dims
embs[:, 17]        # dim 17 across ALL movies — a "feature column"
embs[:3]           # first 3 movies → (3, 384)

# --- Search & compare ---
embs[0] @ embs[1]                   # dot product = cosine sim (unit norm)
np.dot(embs, embs[7]).argmax()       # most-similar movie to movie 7… is 7
(embs @ embs.T).shape               # (5000, 5000) full similarity matrix

# --- Big-file mode ---
embs = np.load("cache/movie_embeddings.npy", mmap_mode='r')  # lazy!
Mental model to keep: an embedding matrix is a spreadsheet where rows are documents and columns are learned, unlabeled features. embs[i] selects a document; embs[:, j] selects a feature; @ compares documents. Everything else in semantic search is bookkeeping that maps those row indices back to documents[i] via your document_map.
Two traps: (1) embs[i] aligns with documents[i] only because build_embeddings encoded them in order — scramble one list and the mapping silently breaks. (2) A slice like embs[:10] is a view: writing to it mutates the parent array. Use .copy() when you want isolation.
